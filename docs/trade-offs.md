# Trade-offs

Every choice below gives something up. Each row says what was chosen, what it costs, and what to do when the cost starts to matter. What was left out of the product on purpose is in [requirements.md](requirements.md). Query timings are in [performance.md](performance.md).

## Data and money

| Choice                                                        | What it costs                                                                                                                                                                     | When it matters, and what to do                                                                     |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Money is stored as whole minor units (cents, paise)           | Amounts must be converted for display and entry. Currencies with no minor unit (such as JPY) are not supported without extra handling.                                            | Adding such a currency: handle its minor-unit size per currency before adding it.                   |
| Salary history is append-only, enforced by a database trigger | A mistake cannot be edited: it is fixed with a new `correction` record, and the wrong row stays visible.                                                                          | If corrected rows clutter the history: hide them in the screen. The records themselves should stay. |
| Employees are deactivated, never deleted                      | The table only grows; "deleted" people still count in the data.                                                                                                                   | A legal erasure requirement would need a separate, deliberate process.                              |
| A fixed exchange-rate snapshot, not live rates                | Rates are illustrative and drift from the real market. Reports are consistent and repeatable, but not current.                                                                    | If real money decisions depend on it: add dated rates and convert each record at its own date.      |
| A salary's currency is set by the employee's country          | If an employee changes country, their old records stay in the old currency (the history is true to what was paid). The current salary uses the new currency from the next change. | Needed for transfers between countries: add an explicit "transfer" flow that records both.          |
| Country, department and job title are constants in code       | Changing them is a code change. Departments are plain text in the database.                                                                                                       | HR wants to manage them: move them into tables with an admin screen.                                |
| Salary changes are refused for inactive employees             | Back-dating a correction for someone who has left needs the employee to be reactivated first.                                                                                     | Frequent in practice: allow corrections for inactive employees only.                                |
| Effective date may be up to tomorrow (UTC)                    | A change dated further ahead is refused, so a typo like 2062 cannot slip in. Planned raises more than a day ahead cannot be recorded.                                             | Planned raises needed: add a "scheduled" state, with rules for when it takes effect.                |

## Insights

| Choice                                                              | What it costs                                                                                                                                                                                                  | When it matters, and what to do                                                     |
| ------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Dashboard covers active employees only, in US dollars               | No view of past payroll, or of people who left. Local-currency figures are only on the employee pages.                                                                                                         | Trend or leaver analysis: store snapshots over time.                                |
| Outliers compare against peers (job title, level, country)          | About 15% of people sit in peer groups smaller than 5 and are never judged. On the seeded data the rule found 110 of the 118 planted outliers in groups it can judge (93%), and flagged 0.9% of everyone else. | Small groups matter: widen the peer group (drop country, or group levels together). |
| Outliers are a reason to look, not a verdict                        | The rule cannot know why someone is paid differently (a rare skill, a contract role). The screen says so.                                                                                                      | HR wants to record "reviewed, fine": add a way to dismiss a flag.                   |
| Outliers are computed in application code over all active employees | Fine at 10,000 people (about 40 ms). It would not scale to millions of rows.                                                                                                                                   | Much larger data: compute in SQL, or precompute on a schedule.                      |
| Charts are plain HTML, not a chart library                          | Only bars and a histogram. No zoom, tooltips or export. Smaller, faster and fully accessible to screen readers and tests.                                                                                      | Richer charts needed: add a chart library for that screen only.                     |
| No caching of dashboard figures                                     | Each visit runs the queries (30 to 60 ms each at 10,000 employees). Figures are always current.                                                                                                                | Ten times the data or many users: cache briefly, or precompute.                     |

## Performance

| Choice                                                      | What it costs                                                                                  | When it matters, and what to do                                                                        |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Paging with page numbers (offset)                           | A deep page is slower: page 380 takes about 34 ms because the skipped rows are still read.     | Pages in the thousands: switch to keyset paging.                                                       |
| Search uses an escaped pattern match, no trigram index      | A search by part of an email takes about 19 ms. No extension to install.                       | Much more data: add the `pg_trgm` extension and an index.                                              |
| The current salary is looked up, not stored on the employee | One extra lookup per row, always correct. No second copy that could disagree with the history. | Much more data: store it on the employee row, kept in step by the same transaction that adds a record. |
| One name index                                              | Slightly slower inserts. Makes the default view (by name) 5 to 7 times faster.                 | Revisit when the default sort changes.                                                                 |

## Security and accounts

| Choice                                               | What it costs                                                                                                                                               | When it matters, and what to do                                                      |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| One user, from environment variables                 | No sign-up, password reset, roles or audit of who changed what. Changing the password means a new hash and a restart.                                       | A second person needs access: add users, roles and a "changed by" column on records. |
| A signed token in an `httpOnly` cookie, not sessions | A copied token stays valid until it expires (8 hours by default, at most 7 days); logout only removes the cookie. Changing `JWT_SECRET` ends every session. | Sensitive deployments: add a session store so logins can be revoked.                 |
| `SameSite=Strict` cookie, one site for web and API   | The web app and API must be served from the same address. No CSRF token is needed.                                                                          | Separate domains needed: use CSRF tokens and `SameSite=Lax` or `None`.               |
| Login limit counted in memory, per address           | The count resets when the service restarts, and each running copy counts separately. Behind a proxy it needs `TRUST_PROXY` set so it sees real addresses.   | More than one running copy: keep the count in a shared store.                        |

## Building it

| Choice                           | What it costs                                                                                                                                           |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Plain SQL with `pg`, no ORM      | More SQL to write and read. In return every query is visible, tunable and parameterised, and the statistics and ranking queries are natural to express. |
| A monorepo with a shared package | One install and one set of types, but the API build must bundle the shared package (done with esbuild).                                                 |
| Native `<select>` for filters    | Less polished than a custom dropdown. Works with the keyboard, on phones, and in tests without extra work.                                              |
| No code-splitting yet            | The web bundle is about 620 kB (192 kB compressed), so the first load carries the dashboard too. Splitting it is the next step.                         |
| Tests that create their own data | A little more set-up per test. No test depends on another, and they run in any order.                                                                   |
